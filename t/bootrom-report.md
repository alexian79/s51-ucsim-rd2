The element is `cl_hw(HW_TIMER, RD2_BOOT_ID 16, "boot")`. **Id 16 was chosen against the
headers, not against serial.cc's dispatch list**, as Main's SPI lesson required:
`rd2_brgcl.h:30` `RD2_BRG_ID 13`, `rd2_kbdcl.h:44` `RD2_KBD_ID 14`,
`rd2_spiccl.h:44` `RD2_SPI_ID 14` in this base (Main has moved SPI to 15 in `~/s51/vendor`),
so 15 is taken in the merged tree and 16 is free either way. The rationale is in the header
comment of `rd2_bootcl.h` as well.

`exec_inst()` intercepts on the **instruction boundary**, not by hooking the read of the
cell at `FFF0h`: the core fetches that byte in order to execute it, so a read hook would run
the API on a console `dump rom` of the vector and on any `MOVC` of it, and a flash array that
answers a read by erasing blocks is not a memory. With ENBOOT set the API runs and
`instruction_22` performs the RET the caller relied on ("The jump at the USER_CALL must be
done by LCALL instruction to be able to comeback in the application", printed p.112). With
ENBOOT clear the call is named, counted and refused, and the byte the array holds at `FFF0h`
is fetched and executed like any other byte. Interrupts are left alone on purpose: "The
interrupts are not disabled by the bootloader. Interrupts must be disabled by user prior to
jump to the USER_CALL" (section 24.10.2, printed p.112).

`cl_uc89c51r` (the AT89C51RB2/RC2 half of the class) is untouched: `boot_hw` is null there,
so the extra cost on that part is one compare against zero, and `-t 89C51R` gains no element
(proved by the suite).

## 2. The mapping questions, answered from the datasheet

* **Window: `F800h–FFFFh`, 2048 bytes.** Table 8-1, printed p.21, on AUXR1.5: "Cleared to
  disable boot ROM. Set to map the boot ROM between F800h - 0FFFFh." Both ends come from
  that row; the size is corroborated by Features, printed p.1, "2048 Bytes Boot ROM", and by
  Table 24-1 printed p.94 (BLJB=0 → boot vector at `F800h`).
* **Which space: program/code space, so both fetch and `MOVC` answer out of it.** Section 24
  (printed p.93) describes the array as "program memory" and section 24.1 promises
  "Byte-wise read without wait state", i.e. `MOVC` reads the same space the core executes
  from. One `cl_address_space` ("rom") serves both, so the banker covers them together.
  `MOVX` is unaffected — external data has its own space (section 9) and its own banker on
  AUXR.
* **Visible while executing from it: yes.** A banker re-decodes the cells it owns, so reads
  of the window while the ROM is mapped see the ROM, which is what the suite exploits to
  observe the mapping without touching the API. And ENBOOT must be set for the `LCALL` to
  reach the ROM at all (section 24.10.1, printed p.112) — there is no way to execute the ROM
  with it clear.
* **Cleared by:** software writing AUXR1.5=0 (table 8-1, printed p.21), and by reset when the
  BLJB fuse is set (figure 24-5, printed p.101). Table 3-11 (printed p.8) lists AUXR1 as
  `0XXX X0X0b`, bit5 **X**. The fuse is not modelled, so the model resolves that X to
  **cleared**: the boot ROM is **inert by default** and every leg of the suite starts that
  way. (Consequence worth knowing: a program that wants the API must set bit5 itself, and
  the suite always has it set by the program, never by the console.)
* **DPTR0/DPTR1 are read from the chip, not from the live pointer.** The API rows of table
  24-10 name DPTR0 and DPTR1 explicitly, so the implementation reads both banks out of
  `dptr_chip` (offsets 0/1 and 2/3) regardless of DPS. The suite pins this: with DPS set the
  call still answers from DPTR0 while `DPL` follows DPTR1 — one register, two masters, and
  the ENBOOT banker's mask (`0x20`) never disturbs the DPS banker's (`0x01`).

## 3. The tWRITE decision — explicit, and logged in the binary

**Decision: PROGRAM BYTE, PROGRAM PAGE and ERASE BLOCK return instantly, burning 0 cycles.**

Why, and what it costs:

* Table 25-7, printed p.115 gives tWRITE as min 7 ms / max 17 ms and leaves the **typical
  column blank**. There is no number in the book to implement.
* Any value picked from that range is enormous: at 24 MHz a stall is 140 000–340 000
  oscillator periods per *machine cycle* — 14 000–34 000 machine cycles (Fosc/12),
  28 000–68 000 in X2, 408 000–1 020 000 oscillator periods. (The plan's "~1M machine
  cycles" overstates it by 12×; the correct figure is ~1M *oscillator periods*.) A fabricated
  stall of that size would corrupt every timing leg in the tree — UART bit times, PCA and
  timer periods, the CKRL prescaler ratios — to represent something no test can observe.
* The boot ROM **binary** is not in doc4235K, so the cycles the real ROM spends cannot be
  attributed to instructions anyway. The ROM is modelled as 2048 bytes of `ffh` for that
  reason, and the instrument says so.
* Where the decision is recorded, so it cannot be mistaken for an oversight: the header
  comment of `rd2_bootcl.h`, the `user_call()` comment in `rd2_boot.cc`, and the instrument —
  `info hw boot` prints
  `tWRITE=0 cycles: PROGRAM/ERASE return instantly by decision (7-17 ms, table 25-7 p.115, has no typical value)`.
* What would change the answer: a real ROM image or a vendor note giving a typical tWRITE.
  `leg_timing_decision` exists so that the day someone models the stall, a green suite turns
  red with an explanation instead of the choice quietly reversing.

## 4. Commands implemented (table 24-10, printed pp.112–113)

| R1 | Command | Model |
|---|---|---|
| `00h` | READ ID via DPTR0 | `0000h..0003h` → `58h / D7h / ECh / EFh` (table 24-3, printed pp.95–96). Any other DPTR0: ACC is left answering the erased byte `0ffh` **and the transcript says the selector is not listed** — inventing an ID for an unlisted selector was the failure mode worth refusing. |
| `01h` | ERASE BLOCK | DPH ∈ {`00,20,40,80,C0`} → that block filled with `ffh`, geometry straight from table 24-9 (printed p.111) as a lookup, **never `0x10000/5`**: block0 `0000–1FFF`, block1 `2000–3FFF`, block2 `4000–7FFF`, block3 `8000–BFFF`, block4 `C000–FFFF` (16K). ACC = DPH, per the row. A DPH outside the set erases nothing and says so. |
| `02h` | PROGRAM DATA BYTE | value from A at DPTR0, written outright — section 24.2 (printed p.93) "The programming of a byte or a page includes a self erase before programming", so a bit-AND into the old contents would be wrong. ACC=0 DONE. |
| `09h` | PROGRAM DATA PAGE | A = count 1..128, DPTR0 = flash address, **DPTR1 = XRAM source** (read through `xram`, not the internal bank). A request that would leave its 128-byte page is refused with the row's own wording and ACC is not written. |
| other | — | logged as not implemented, ACC left unchanged. |

No chip erase: Full Chip Erase (`07h`) belongs to the ISP command set of table 24-9 (printed
p.111), not to the API. There is also **no READ command and no ERASE PAGE command** in the
API — "ERASE" appears on exactly one page of doc4235K, and reading the array is `MOVC`
("Byte-wise read without wait state", section 24.1, printed p.93). A suite leg asserts that
`R1=07h` does not wipe the array.

**Out of scope, deliberately:** the host-side backing file for the array (persistence across
simulator *processes* — bytes do survive `reset` inside one run, which is asserted), the
BSB/SBV/SSB security levels, the fuse bytes `0Ah`, HSB `0Bh`, boot ID/version `0Eh/0Fh`, the
section 24.9 serial bootloader, parallel programming mode, and the BLJB fuse itself.

## 5. Suite — `t/bootromtest.py`, 68 checks, all green

```
S51_SIM=/tmp/ucsim-boot/ucsim/src/sims/s51.src/ucsim_51 python3 t/bootromtest.py
Checks run: 68  Failed: 0
ALL BOOTROM CHECKS PASSED
```

`t/floor.sh` does **not** run it (`floor.sh` was not to be touched, and its suite list is
hardcoded plus `kbdtest/spitest/ckrltest`), so this command is the manual step.

Anti-vacuity, because a leg that passes without the feature proves nothing:

* every flash cell an API command targets is **seeded** by the loader, so a read-back names
  the cell it came from (an untouched cell is `0ffh`, and no ID answer is `0ffh`);
* ACC is seeded `0a5h` before every call, so "ACC unchanged" and "ACC = the row's value" are
  different observations and neither can be a zero nobody wrote;
* the array carries a stub at `FFF0h` (`INC A ; MOV P0,#02eh ; RET`) in every image. Its
  first byte `0fh` can be neither an erased cell (`0ffh`), an empty image (`00h`) nor an
  opcode the program body shares. **Inverted pair:** one image, only the AUXR1 byte differs —
  ENBOOT set ⇒ ACC=`058h` and P0 stays `0ffh` (the stub was never fetched); ENBOOT clear ⇒
  ACC keeps `0a5h` and P0=`02eh` (the array ran) plus a refusal naming USER_CALL and ENBOOT.
* erase geometry is pinned from **outside** the block too: erasing `DPH=20h` clears `2000h`
  and `3FFFh` while `1FFFh` and `4000h` keep their seeds; `DPH=C0h` clears `C000h`, `C123h`
  and `FFF8h` while `BFFFh` keeps its seed. A `64K/5` model dies here.
* mapping is proven at **one address, A/B/A**: `dump rom 0xfff0` = `0f` (array) → `ff` (ROM,
  after `set memory sfr 0xa2 0x20`) → `0f` again. Same program, no API involved.
* `MOVC` of the vector with and without ENBOOT, from one program, proves the ROM is in code
  space; and P0 staying `0ffh` through both readings proves a *read* of the vector runs
  nothing — which is exactly why the interception is not a memory hook.

**Control audit.** `S51_SIM=/tmp/s51-ref-b python3 t/bootromtest.py` (the pre-boot-ROM
binary) runs 65 of the 68 checks — the element leg returns early once the element is missing,
so three of its checks never execute — and **fails 40 of them with named reasons**: no `boot`
element, `set memory sfr 0xa2 0x20` leaves `FFF0h` answering `0fh`, all four ID legs read the
seed `0a5h`, nothing is erased, nothing is programmed, the instrument prints nothing.

The 25 that pass there are exactly the legs that are not evidence of the feature, and naming
them is the point of the audit: the three absence legs (`-t 89C51R has no boot element`, and
the three `leg_reference_proof` legs about the control's own flat mapping and silent call),
the legs whose assertion is that *nothing happens* (ACC keeps its seed, a refused call leaves
the array alone, both neighbours of an erased block keep their seeds because nothing was
erased, `R1=07h` leaves ACC unchanged), the legs that read the array through `MOVC` without
the API in the path, and `leg_timing_decision`'s clock comparison — equal clocks on a binary
with no API at all, so that check is a control-passer by construction, which is why the
decision is pinned a second time by the adjacent instrument-text check that *does* fail on
the control. In other words: no leg that asserts something the boot ROM does survives on the
control binary, and every leg that passes there is one the boot ROM's presence or absence has
no bearing on.

Traps hit while writing it, recorded in the module docstring so the next reader does not
re-inherit them: `file` must be quoted (an unquoted path loads nothing and the all-zero
image "runs" as NOPs); `dump sfr` needs an explicit range and there is no `set sfr` command
but `set memory sfr <addr> <val>` works; the code space is `dump rom`; dump rows print the whole
aligned group so a one-byte probe must dump one byte; P0–P4 reset to `0ffh` and
`dptr_chip`/iram come up uninitialised, so every input is stamped by the program; the console
echoes into the same stream and can splice in front of an output line, so no probe regex is
line-anchored; and **the API costs two instruction slots** (the `LCALL`, then the ROM's own
`RET`) while a refused call costs three (the array's stub) — which is why the legs park in a
self-jump and overshoot instead of counting steps. Only the timing leg counts exactly, and
both of its runs take the same path (204 clocks each, measured).
